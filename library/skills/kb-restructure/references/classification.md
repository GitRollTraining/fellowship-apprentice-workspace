# Classification — live vs historical

Every refscan hit gets a LOGGED verdict before anything is fixed. Refscan hints are pattern-derived suggestions; the verdict is the agent's, made against this rule, one log row per hit.

Verdicts: **live** (fix per the operation's ref-mapping) · **historical** (leave alone — rewriting a point-in-time citation falsifies the record and is itself a defect) · **not-a-ref** (the text does not denote the target at all). The core test where no rule below decides: **is this text a pointer a reader follows today, or a citation of what was true when written?**

## Precedence — apply top-down, first match wins

0. **Identity screen.** Does the matched text actually denote the target path? A superstring path (`alpha/beta-archive/`), a same-named different file, or a coincidental string → `not-a-ref`, stop.
   **Syntax specimen = a PLACEHOLDER.** A path is a specimen only if it contains a metavariable a reader is meant to substitute (`{slug}`, `{{x}}`, `<name>`, `path/to/thing`) → `not-a-ref`; optional editorial refresh, not a ref-fix.
   **A CONCRETE path is a real ref — even if it is currently DEAD.** Do not use "it does not resolve" as a specimen test: a dead concrete path is a BROKEN POINTER, which is a defect to fix or log (playbook step 5), not a thing to ignore. (A live run's flagship template fix was exactly such a link — an Exemplar pointing at a real file via a wrong relative depth, dead for months. A "does-not-resolve → not-a-ref" screen would have left it dead, re-creating the very defect this skill exists to catch.) Nor is "it lives in a template" a test: templates carry real Exemplar links, "see also"s, and canonical-source references. **Placeholder, or it is a real ref.**
1. **Machine-regenerated bodies** (sync snapshots, compiled digests).
   **SCOPE — apply rule 2's container test FIRST. Rule 1 fires only OUTSIDE a frozen container.** A machine-derived body that sits INSIDE a frozen container (`.archive/` tree, workspace historical pattern) is FROZEN: `historical`, header tag only, body never edited — go to rule 2 and stop. (Scoped 2026-07-13: rule 1 sits above rule 2 in a first-match-wins lattice, so its DORMANT branch below was emitting `live` for machine-derived bodies that had ALSO been archived — and a dormant pipeline is exactly what an archived program has. That combination licensed editing a frozen archived body, which rule 2, kb-sop § Archive, and the archive playbook's gate 6 all forbid. Rule 2's only exceptions are rules 3, 4, and 5 — rule 1 is NOT one of them. NOTE the DORMANT branch is still the right call for a dormant program's digest that is NOT archived: dormant does not imply archived, and an unarchived derived body with a dead pipeline must be edited directly or its links rot forever.)
   Outside a frozen container, ask: does an owning pipeline re-derive this file's stale field? Three branches — a compiled file is not automatically leave-alone:
   - **A live pipeline re-derives it** → `historical (leave)`, note "regenerates via its own pipeline"; a forward pointer inside a generated body gets fixed in the SOURCE document, never the generated body — hand-edits break the pipeline's own drift detection.
   - **The compiled file IS the system of record** (a records/registry file) → `live`; direct edit IS the pipeline route; name the owning pipeline in the rationale.
   - **The pipeline exists on paper but is DORMANT or ABSENT** — nothing will actually re-derive this body (the program it serves is retired, the regenerator was never built, or it runs only on a trigger that will not fire) → `live`, direct edit; state WHY the pipeline is dead. A "Compiled" class label is a claim about how the file *should* be maintained, not evidence that anything still maintains it. Leaving a derived body's links dead because a hypothetical regenerator "owns" them is how a KB rots.
   - Pipeline CONFIG (frontmatter fields, registry entries) carrying the old path is always `live` — fix the config.
2. **Frozen containers**: `.archive/` trees, workspace historical patterns (loaded at preflight from the workspace's rename/move policy section), Immutable and append-only classes per the parent manifest → `historical` — INCLUDING manifests inside them: an INDEX.md inside an `.archive/` tree is part of the frozen record. Exceptions: rules 3 and 4 — **and rule 5**.
   **LIVE AUTHORITY WINS OVER A HISTORICAL PATTERN.** Before freezing, check the workspace policy's live-authority list (rule 5). A records file, a registry, or a live manifest that ALSO happens to sit under a historical pattern is still LIVE — freeze it and the KB's own system of record goes stale, which is worse than any over-fix. Policy patterns are coarse (a whole directory); the live-authority list is exact (a named file). Exact beats coarse. (A live workspace's coarse historical pattern for a transcript tree also matched the records file that the same policy names as live authority — freezing its own system of record.)
   **The manifest's CLASS field decides — not its prose description.** A manifest row whose *description* reads "archived research planning" while its *class* column is blank or Mutable does NOT freeze that directory. Read the class; check whether workspace policy names the path. If neither says frozen, the container is NOT frozen — fall through to rules 7-8 (host precedent first, then the core test) and judge the hits on their own merits. (A live run froze three files on a description alone; workspace precedent had in fact been fixing them. A directory whose name merely *sounds* retired — `.planning/`, `old/`, `legacy/` — is not a frozen container.)
3. **Navigation-pointer function test.** **SCOPE: this rule fires ONLY on a hit inside a FROZEN container (one rule 2 already froze).** It is the escape hatch out of rule 2 — nothing more. On a hit in an UNFROZEN container it does not apply at all; skip to rule 4. (Scoped 2026-07-13: as originally written its negative half — "body prose is a citation → historical" — silently fired on every unfrozen doc too, and since the lattice is first-match-wins it pre-empted rules 7-8 entirely, making them dead code. It froze exactly the files a live run had to fix.)
   **Append-only operative records are exempt from this rule.** If the frozen container is an append-only record (a log, a changelog, a run record — rule 4), a routing-shaped line inside it is STILL fixed append-only: add an old→new mapping line, never rewrite the existing one. Rule 4's entire purpose is that guard, and rule 4 sits BELOW this rule in a first-match-wins lattice — so without this exemption, rule 3 would emit `live, fix it` and the rewrite would falsify what the past run recorded. Same verdict, different fix: the fix is the point.
   **Machine-regenerated bodies are exempt from this rule, frozen or not.** If the hit sits in a body some pipeline re-derives (a sync snapshot, a compiled digest), a forward pointer inside it is fixed at the SOURCE and the body is never hand-edited — see rule 1. Rule 3 must never be read as licence to edit a generated body: a hand-edit there breaks the pipeline's own drift detection, and the next regeneration silently reverts you. (Restored 2026-07-13: scoping rule 3 to frozen containers accidentally dropped this, and a frozen snapshot containing "now lives at" then inverted to `live`.)
   Within a frozen container, for a NON-generated body: a line whose PURPOSE is routing today's reader OUT of the frozen record and onward to LIVE content — supersession headers, archive-README forward pointers ("Canonical:", "now lives at", "Relocated:", "superseded-by", a bare markdown link in a batch README pointing at the successor) → `live`; fix it even though its container is frozen. The label list is exemplary — function decides, not the label.
   **It must route OUTWARD.** A frozen manifest's own INVENTORY rows — the rows describing what sits beside it inside the batch — are not outward routing; they are the frozen record's description of itself, and they stay `historical` (this is what rule 2's "manifests included" means). The test: does this line send the reader to content that is still LIVE (→ fix it), or does it describe the frozen batch's own contents (→ leave it)? In-sentence mentions inside the frozen doc's body prose are citations, not routing → they stay `historical` (which is where rule 2 already put them; a dated briefing row-linked from a live INDEX keeps the doc reachable, but that does not make its inner narrative live — fix the INDEX row if the DOC moved, leave the prose). (Rule 1 cannot collide with this rule any more: rule 1 fires only OUTSIDE a frozen container, rule 3 only INSIDE one. A forward pointer inside an UNFROZEN generated body is rule 1's business — fix it at the source.)
4. **Append-only operative records** (error logs, changelogs, run logs that FUTURE runs consult as instructions) → `live`, but the fix is APPEND-ONLY: add an old→new mapping line; never rewrite existing lines.
5. **Live manifests and authority files**: INDEX.md (or equivalent) outside frozen containers; files the workspace policy names as live authority (records files, registries) → `live`.
6. **Sidecars** → `live`. A sidecar is a gitignored COMPANION whose name derives from its main file's stem (`{stem}.<class>.md` style) or that the workspace declares as a companion — it reconstructs its main file and must move with it (fix the reference AND physically move the companion). Every OTHER gitignored file is ordinary content: classify by these rules, fix its text in place, never relocate it just for being gitignored.
7. **Host-KB precedent** (checkable; use it before falling back to judgment). Does the KB's own record show how it classified THIS file — or this class of file — during a PRIOR mutation? Migration notes, historical-note blocks in manifests, and past batch READMEs routinely say so outright ("citations in X / Y / `dir/*.md` have been updated to point at the new paths"). If it does: **follow that precedent**, or overrule it explicitly and log why. A KB that treats the same file as frozen in one mutation and live in the next is incoherent in a way that neither choice alone would be — and the precedent is evidence about what the host KB considers a live pointer, which beats an outside guess. Absent any precedent, go to rule 8.
8. **Remainder** → judgment via the core test. The date on a document does not freeze it; what the path is DOING in the line decides:
   - **Communication / claim snapshots** (briefings, meeting notes, dated analyses, sent correspondence): body prose citing the old path is recording what was said or believed at a time → `historical`. Rewriting it falsifies the record.
   - **Working records of a program** (plans, progress logs, validation reports, deliverable inventories): the path is an ARTIFACT LOCATOR — it tells a reader where an output lives, and that output still exists under its new name. A reader follows it → `live`. The date stamps when the work happened, not what the file is called.
   - Where the two readings genuinely tie, prefer the one the host KB's precedent (rule 7) already chose; if there is none, prefer `historical` — over-fixing a citation is the more damaging error, because it destroys evidence, whereas a stale locator merely inconveniences a reader.
   - (Rule 3 is NOT in play here: it fires only inside a frozen container, and rule 8 is only reached for unfrozen hits. An unfrozen navigation line needs no exception — it is simply a live pointer.) Log verdict + one-line rationale.

## Self-reference

Two sources of designed self-hits. Both must be pre-logged BEFORE verify — an unlogged self-hit fails the residue gate.

1. **The run's own artifacts.** The verdict log and report cite old paths by design. If they live inside the KB tree, the verify-phase rescan hits them: pre-log each, verdict `historical`. (Better: keep them outside the tree, or `!`-exclude their directory in the policy file.)

2. **The run's own FIXES.** A correct fix routinely re-introduces the old path string. These are not residue to chase — they are the fix working as designed. Pre-log each. Four shapes, all observed in a single live run:
   - **Append-only mapping lines** (rule 4): the preserved original line still names the old path — that is the point.
   - **Strike-through resolutions**: a backlog or tracker item struck as done retains its original wording, old path included.
   - **Provenance notes**: an archive-batch manifest records what was migrated FROM.
   - **Migration / supersession notes**: a manifest or convention line that records the retirement necessarily names the retired path.

   The test: does this occurrence POINT a reader at the old location, or RECORD that the old location existed? Pointing → still a live ref, fix it. Recording → designed, log it and move on.

   **Verdict value for these rows: `live`.** They are hits that RECEIVED a fix — the fix simply happens to preserve the old string (that is what an append-only mapping line, a strike-through, or a provenance note IS). They are NOT `historical`: a historical verdict means "left untouched", and these were touched. They belong in the LEAVE-SET (the set of files that still contain the old path at the end) precisely BECAUSE their correct fix preserves it. Leave-set != historical + not-a-ref; see § Verdict log format.

## Verdict log format

| Path | Hint | Verdict | Rationale |
|---|---|---|---|

One row per hit; verdict values exactly `live` / `historical` / `not-a-ref` (append-only fixes are `live` with "fix: append" in the rationale). The log travels with the run report / commit body.

**The LEAVE-SET is not the same as the historical + not-a-ref rows.** It is every file that legitimately STILL CONTAINS the old path once the run is finished. That includes rows verdicted `live` whose correct fix PRESERVES the old string — an append-only mapping line (rule 4) keeps the original line verbatim; a strike-through resolution keeps the item's original wording; a provenance or migration note names what was retired. It also includes files the run itself CREATED. Build the leave-set explicitly, and gate residue as SET EQUALITY against it in both directions: an unlogged residue hit means a missed ref, and a leave-set file that no longer carries the old path means something was silently over-fixed. Both are failures.
